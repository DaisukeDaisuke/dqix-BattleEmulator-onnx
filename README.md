# DQIX Battle Emulator — exact ONNX graphs

DQ9 の戦闘規則を、小さな決定論的 ONNX グラフと宣言的な実行順序で表す開発中のエミュレータです。学習データから結果を近似するモデルではありません。乱数状態、分岐、丸め、HP・MP、状態持越しを明示的なテンソル計算として実装します。

最終的な判定根拠は元 ROM の Ghidra 実行と対応するデコンパイルです。従来のバトルエミュレータは独立した比較対象として使用し、その誤差や省略を新しい規則へ取り込みません。全ゲーム・全構成への対応は未完了です。

## HTML を使う

[Hugging Face の成果物](https://huggingface.co/RabbitDaisuke/dqix-BattleEmulator-onnx/tree/main)から `dq9-battle-emulator.html` をダウンロードしてブラウザーで開きます。戦闘・カメラ・単体グラフを選び、初期条件、開始 seed、件数、ターン上限を指定できます。初期条件の JSON は編集可能です。

戦闘の CPU 経路は生成されたグラフを直接 WebAssembly に変換し、GPU 経路は同じグラフを WGSL に変換して常駐状態を更新します。生成するグラフは標準 ONNX 形式です。戦闘の算術規則を別の C++ 実装へ書き直していません。

戦闘モードは外部ランタイムのダウンロードが不要です。単体グラフ・カメラの CPU 実行で `GatherElements` を使用するモデルは、ビルド時に `cpuExecutionProvider: "onnxruntime-wasm"` と明示し、ONNX Runtime Web **1.31.1** を jsDelivr から読み込みます。GPU を選択した場合、これらのモデルは従来の GPU 経路で実行します。binary64 を必要とするカメラの1モデルは、GPU 選択時も画面に明示した CPU 経路を併用します。宣言にない実行時の CPU フォールバックは行いません。

計測結果ではコンパイル・初期化と実行時間を分けます。GPU 機種とバッチ数によって速度は変わります。ソフトウェア WebGPU の計測値から実機 GPU の速度を推定したり、単一の乱数演算の速度を戦闘全体の処理速度として扱ったりしません。

加えて、6つの明示的なカメラ実行モードと単体グラフを収録します。新しい `rom-level-scaled-selector43` と `rom-vacuum-action-core2` は、しんくうはの数値処理・実行部分を扱う単体モデルです。これらの存在だけでゲルニック将軍の戦闘全体が完成したとは扱いません。

戦闘は検証済みの味方1人・敵1体の数値条件を中心としています。味方の手動通常攻撃、各敵の対応済み行動、状態変化、終了判定を実行します。任意の編成・装備品ID・全アイテム操作・全ての旧構成は未対応です。カメラは明示的な別フェーズであり、カメラが消費する乱数を除外した結果をゲーム全体との一致とは呼びません。

AI 探索とターン数には明示的な上限があります。未対応入力、探索上限、まだ継続中の戦闘は区別し、勝ち・負けへ加算しません。seed の選別は行いません。

## ソースから生成する

Node.js 24 と Python 3.12 を使います。グラフと HTML の生成に npm パッケージのインストールは不要です。

```sh
node scripts/build-release.mjs --out dist
python -m pip install -r requirements-build.txt
python scripts/validate_release.py dist
```

ビルドは数値規則、数値テーブル、入力プリセットから ONNX・グラフ IR・実行プログラム・単一 HTML を新規生成します。ROM イメージ、Ghidra プロジェクト、デコンパイル本文、以前の生成済みモデル、一時的な照合 JSON は必要ありません。

`data/source-authority.mjs` は参照した原資料の SHA-256、`data/camera-constants.mjs` は必要な数値定数とビット表現を保持します。`data/battle-presets.mjs` と `data/giyumei-initial.mjs` は実行に必要な初期条件です。観測された正解出力を計算の代わりに埋め込んでいません。

`dist/release-manifest.json` に全成果物のパス、サイズ、SHA-256、生成元コミットを記録します。検証スクリプトは一覧外のファイルを拒否し、全 ONNX に公式 checker の full check を実施します。`--reuse-generated` はローカルで HTML を調整する場合に限った再梱包用オプションで、CI は常に全生成を行います。

## GitHub Actions → Hugging Face

`main` への push と手動実行で `.github/workflows/convert-release.yml` が動きます。リポジトリの既存シークレット `HF_TOKEN` を publish ステップだけに渡し、検証済みの成果物を `RabbitDaisuke/dqix-BattleEmulator-onnx` に公開します。

公開は現在の Hugging Face 親コミットを指定した1回の追加コミットです。既存ファイルの削除は行いません。公開後は返された不変のコミット ID から全成果物を読み戻し、サイズと SHA-256 を検証します。GitHub には生成に必要なソースを置き、生成モデルと HTML は Hugging Face に置きます。

## なぜ行列・重みで表せるのか

決定論的な状態遷移なので、状態と乱数を入力にすれば出力も一意に決まります。行列だけで一度に表すと、比較・条件分岐・丸め・可変回数の処理が巨大化します。この実装では MatMul、比較、選択、Gather、明示的な状態更新を組み合わせます。行列回転によって未知の規則を学習させる必要はありません。

64 bit 乱数は byte 単位の小さい整数へ分解し、binary32 の厳密な整数領域で計算します。モデルの値域契約とランタイムの入力検査を保ち、単純な float32 化による桁落ちを避けます。大きな処理は共通の小モデルへ分け、各 seed を独立した GPU レーンとして並列実行します。

CPU/GPU の処理能力だけでなく、演算の分割数、ディスパッチ回数、転送量、常駐メモリが速度を左右します。そのため、正確性を確認した共通グラフを使いながら、GPU ディスパッチの削減と固定重み形式の小型化を別々に検証しています。
