# 共通カメラの12体入力と row+4 境界

この実装は、戦闘状態に必要なカメラ目標・経路・関連フラグの共通計算を扱う。描画装置、フォント、メッセージ文字列、スタック履歴から row+4 を生成する処理は要求しない。モデル生成にも、モデルとHTMLの実行にもROMの読込みは必要ない。開発時の原本照合だけが、別途復元したROMとGhidraを使う。

## 容量と値の意味

元の `func_ov025_021dffac` は12行のカメラ名簿を持つ。行順は既存パーティの順序、その後に敵IDの昇順である。共通グラフは12体分のテンソルを使用し、有効行数とIDを別途保持する。敵・ボスごとの計算プログラムを作らず、同じ遷移に編成・行動・座標などのデータを入力する。

各実行境界で、実際に存在するコンパクト行ごとに1個の符号なし32ビット値を外部入力する。すべての `0..4294967295` が有効である。モデルへ渡す際には4個の8ビット要素へ分解するため、Float32による32ビット値の丸めを起こさない。未使用テンソル行のゼロは配列整形であり、不明な実在行をゼロに固定することを意味しない。

同一呼出し内の競合処理が row+4 に1を書いた場合、その計算結果を後続処理へ渡す。外部候補を毎段階で再注入しない。別の実入力境界は新しい境界IDで探索し、すべての整合する枝がそれまでの計算済み状態を引き継ぐ。

## 入力を要求する直前の判定

`createCameraRow4BoundaryPlanner({getModel, runGraph, capacity:12})` が返す `run({rows})` は、状態を書き換えずに次の3つのONNX計算を行う。

1. 外側の入口で現在の行動と先頭参加者が存在するかを判定する。
2. 特殊戦闘800/801の名簿選択と、party0によるdispatcher回避を判定する。
3. 行動定義、source/targetの存在と相違から、目標dispatcherが本当に動くかを判定する。

結果は `{boundaries, graphCalls}`。各要素は次の形になる。

```js
{
  kind: 'camera-row4',
  required: true,
  wordCount: 5,
  rowIds: [0, 1, 2, 3, 192],
  compactRowIds: [0, 1, 2, 3, 192],
  dispatchEnabled: true
}
```

`required:false` の場合は `wordCount:0`、`rowIds:[]` であり、探索枝を増やさずに呼出しを進める。例えば特殊戦闘でparty0がsourceの場合、対象が存在しない場合、sourceとtargetが同じ場合が該当する。`compactRowIds` は実際の名簿を説明する情報であり、不要な行を探索変数へ追加する指定ではない。

親処理そのものの入口から判定する用途に限り、`fromOuterEntry:false` を明示すると外側入口の判定を省き2グラフになる。製品の通常の呼出しは既定の外側入口から判定する。

判定はRNGを消費せず、座標や保持状態を更新しない。`dispatch-init` の計算結果のうち `active` だけを使用する。実際の目標、最近傍座標、経路、書込みは候補を与えた後の通常のグラフ実行で計算する。

## 行動表の上限

生の行動領域は72件まで表現する。ただし、元の経路計算 `func_ov025_021e0638` は参加者が存在する行動を `int var6[60]` へ圧縮する。したがって、72件の生の領域に対しても実在参加者のある行動は60件以下でなければならない。この条件を超える状態は `supported:false` とする。原本の配列越境を、正常な拡張アルゴリズムとして扱わない。

経路探索の反復予算は完了判定と区別する。12体それぞれの最大15移動に加え、最後の変化しない走査を含めて上限を構成している。予算が尽きた結果を完了扱いしない。

## 生成と接続

```sh
node graph-v2/build-camera-common-capacity.mjs graph-v2
```

この生成器は12個の容量拡張モデルと2個の射線計算モデルを出力する。`cameraParentModelNames(12)` とその呼出し元の共通モデル集合が必要なモデルを列挙する。4体用の旧モデルは明示的に `capacity:4` を選ぶ場合に再現できる。配布時には共通プログラムの依存集合だけを既存の束ねた配布ファイルへ含める。

ホストは状態の配列化、グラフの実行順、入力候補の列挙、照合と保存を担う。名簿の条件判定、行動定義参照、占有、目標・補助node・face、競合の row+4 書込み、経路とフラグ更新はONNXで実行する。

## 検証済みの範囲

2026-11-01の独立した原本実行で、5体・8体・12体の12ケースを検証した。目標関連の5項目×実在行、戻り値、すべての外部 row+4 の保持・書込みを合計678項目で比較し、差分は0だった。5行目より後の row+4 へ実際に1を書くケース、全ビット1、最上位ビット1、過去の複数参加者、対象なしの分岐を含む。

探索制御も同じ実グラフを使用し、明示した小さな検証用候補領域について、原本の出力を照合条件として候補を絞った。元入力の枝はすべて保持され、残った複数候補を勝手に1つへ固定していない。JSONから68回再開して同じ計算済み枝を保持できた。この小さな検証領域を製品の既定候補集合にはしていない。

旧48ケース945項目も12体グラフで差分0、336回のJSON再開を確認した。さらに、実ONNXによる入力境界判定、不要なrow+4入力の省略、旧4体版と12体版の親処理8ケースの同値、12体の親処理完了、72生行動と60実在行動の上限を別の契約検証で確認した。

これらは目標・入力境界と接続の検証である。12体の経路全体、カメラ全体、ダメージと乱数を含む複数ターン全体の原本一致を、この結果だけで主張しない。無効nodeを下流helperへ渡す一部の領域など、残る未対応条件は完了結果に混ぜない。

## メラ系の射線による状態更新

sourceのvisual flag0x80と行動ID9..11が組み合わされる場合、元のdispatcherはsourceとtargetを結ぶ線分に近いnodeを列挙する。これは必要なカメラ状態へ影響する計算なので共通処理に含めた。

`rom-camera-corridor-distance81` は、同じ固定小数点除算、ベクトル積、内積、距離の丸め順で81nodeを計算する。77個の有効nodeのうち、距離が6144未満のものを選ぶ。一般的な浮動小数点の線分距離へ置き換えていない。

`rom-camera-corridor-conflict12` は選ばれたnodeを占有255にし、source/target以外でそのnodeを占めていた行に row+4=1、auxiliary=255 を書く。ほかの入力ビットは保持する。以後の通常行動は、その計算済み状態から続行する。描画やリソース処理を呼ぶ必要はない。

座標域は既存の正確な距離モデルと同じ各成分±4194303。大きな積は8ビット要素に分け、内積の3成分を足してから一度だけ丸める。線分の外へ射影される場合は原本どおり端点距離へ切り替える。この順序により、ゼロ長線分、負の座標、高さがある射線、境界6144を一貫して扱う。
